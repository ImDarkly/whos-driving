# Working agreement

Read GAME.md, SPEC.md and KNOWLEDGE.md before work. Keep durable knowledge in these files; update only what meaningfully changed. Do not duplicate facts across them.

- Oleksandr designs, approves scope, playtests, decides what ships and merges. Codex writes specs, implements, validates and fixes routine technical problems in one main chat.
- Loop: describe intended feel → short spec (scope, non-goals, technical freedom) → scope approval → build and test → playable checkpoint → batched playtest feedback → update observations and decisions separately.
- Routine repairs may proceed autonomously within approved behavior. Changes to controls, handling, difficulty, player experience or scope need Oleksandr's decision with a recommendation and gameplay consequence.
- Experiments remain hypotheses until playtested and explicitly adopted. Tests do not establish fun. Report only executed checks as passed; give limitations and the shortest manual check for anything unverified.
- Think before coding; simplicity first; surgical changes; goal-driven execution. These are a community distillation of Karpathy's observations, not rules he published.
- Delegation is optional per task, never the default. Keep tasks bounded and checkable; handle physics/networking decisions and hard debugging in the main capable session. No router, scheduler or controller project.
- Codex may commit verified work on a working branch. Do not push or merge without explicit authorization; Oleksandr controls merging.
- Start fresh chats at natural milestones and read these notes. Simplify the process if it starts feeling like supervision.

This setup session stays on Sol Medium. Do not alter global settings/profiles, add worktrees or orchestration, install software, sign into accounts, push or merge. Ask only when missing software/access actually blocks the authorized work.
